# C-012 顾问复审收口：AC-05 措辞取舍、瞬态 lint 事件记录与组合命令 fail-fast

日期: 2026-09-25

#### 上下文
顾问复审（adv-9）接受 C-010/C-011 方向并给出五项收口：执行计数比对或撤回「照常执行」措辞；签名比对口径写明；两条报错分支（零 AC、转绿）须 fixture 实跑留痕；AC-05 改写的「零变更」说法不成立（原文「内容应当来源于」是持续属性，新文「当被装配时」把约束锚定到装配时刻，属轻微收窄）；一次瞬态「agentmap lint failed」须记档且组合命令缺 fail-fast 需确认——该组合命令中 lint 失败后 `;` 分隔使后续 add/commit 照常执行，若 lint 真失败则提交未经门禁。

#### 决策
① AC-05 再改写为无时间锚定形态「系统应当使偏好区内容来源于…」（以「系统」开头满足 EARS 正则且恢复持续属性语义），本条即为该 nuance 的接受记录，撤销 C-011 中「零漂移」对 AC-05 的表述；② TAP 三重校验落地：标题集合相等 + 失败签名核对（账本 `expect` 标记须出现在 TAP 详情块——文件级条目的可观察签名为合成条目的 `ERR_TEST_FAILURE`，底层 ERR_MODULE_NOT_FOUND 走 stderr 不入 TAP，如实按可观察签名登记）+ 执行计数核对（计划=失败+通过、且等于账本 baselineExecuted=192，bail-out 立即暴露）；③ 两报错分支经 --self-test 合成 fixture 实跑留痕（零 AC 分支与僵尸预期同场触发、转绿与计划外分支各自触发，输出存于工具自身运行记录）；④ 瞬态 lint failed 事件：三次复跑未复现，最可能假设为同组合命令内 lint --report 与 git add 之间的写后读竞态（前一步刚写入的工作区文件在 ls-files 快照中的可见性时序），无证据支持更深结论；本组合命令确以 `;` 分隔缺 fail-fast——此后多步验证链一律 `&&` 串联，权威门禁以 pre-commit/pre-push hook 本体为准（hook 失败即阻断提交/推送，不依赖组合命令顺序）。

#### 被否方案及原因
- 保留 AC-05「当被装配时」措辞并仅记档：持续属性被收窄为时刻属性是真实语义损失，改写成本低而保留收益为负。
- 将瞬态事件归为「无需处置」：无复现≠无根因，fail-fast 修正与记档是可落地的最小闭环。

#### 影响面
R-02-006/AC-05（措辞）；tools/expected_fail_check.py、tools/anchor_coverage.py（三重校验与自测）；T-011（预期失败清单的机械凭据）
